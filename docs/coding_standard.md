# 嵌入式软件编码规范

## 1. 范围

本规范适用于 Tank 平台新增和修改的嵌入式 C 代码，包括应用模块、协议模块、
通道模块、公共能力模块和硬件适配模块。

项目引入的第三方代码、芯片厂商代码和自动生成代码可保持原有风格，但不得在未隔离
的情况下与项目代码混写。项目代码中，本规范已经明确的事项优先于所在文件的历史风格；
本规范未规定的事项可以保持文件局部风格。修改历史代码时只整理本次任务直接涉及的最小范围，
不得为统一风格扩大修改。

“必须”“禁止”“应”和“建议”的强制程度统一采用 `development_rules.md` 第 2 节定义。模块归属、
依赖方向、公共接口边界以及跨模块、跨产品的设计策略由 `architecture_rules.md` 规定，不属于本编码
规范的职责。

## 2. 总体原则

### 2.1 清晰第一

- 清晰性是易于维护、易于重构的程序必需具备的特征。代码首先是给人读的，好的代码应当可以像文章一样发声朗诵出来。
- 目前软件维护期成本占整个生命周期成本的40%~90%。根据业界经验，维护期变更代码的成本，小型系统是开发期的5倍，大型系统（100万行代码以上）可以达到100倍。业界的调查指出，开发组平均大约一半的人力用于弥补过去的错误，而不是添加新的功能来帮助公司提高竞争力。
- “程序必须为阅读它的人而编写，只是顺便用于机器执行。” ——Harold Abelson 和 Gerald Jay Sussman
- “编写程序应该以人为本，计算机第二。” ——Steve McConnell
- 本规范通过后文中的原则（如头优秀的代码可以自我解释，不通过注释即可轻易读懂/头文件中适合放置接口的声明，不适合放置实现/除了常见的通用缩写以外，不使用单词缩写，不得使用汉语拼音）、规则（如防止局部变量与全局变量同名）等说明清晰的重要性。
- 一般情况下，代码的可阅读性高于性能，只有确定性能是瓶颈时，才应该主动优化。


### 2.2 简洁和单一职责

- 一个模块只负责一类业务。
- 一个文件应具有明确职责。
- 一个函数只完成一件事情。
- 本次修改直接造成的无调用函数、变量和宏必须删除；历史遗留项另建任务处理。
- 重复逻辑应根据业务语义、稳定性和维护成本评估提取，不按出现次数机械抽象。
- 不得为一次简单调用建立无业务含义的转发层。

### 2.3 模块协作

模块职责、依赖方向、接口可见性和产品差异落位统一执行 `architecture_rules.md`。本文件只规定这些
接口和实现采用怎样的 C 语言表达，不重复定义模块边界。

### 2.4 质量优先级

发生取舍时，按以下顺序考虑：

1. 正确性和安全性。
2. 可读性和可维护性。
3. 可测试性和可诊断性。
4. RAM、Flash 和执行效率。
5. 个人书写习惯。

只有经过测量确认存在瓶颈时，才允许用可读性换取性能，并应说明原因。

## 3. 模块与文件

### 3.1 目录

- 模块使用独立目录，目录名采用小写 `snake_case`。
- 模块对外头文件放在公共 `inc` 目录。
- 仅供模块内部使用的头文件放在模块目录，不加入全局头文件搜索路径。
- 模块包含多个职责相对独立的子功能时，可以按子目录组织，并为各子功能提供内部头文件。
- 文件名采用小写 `snake_case`，名称应简短并能表达职责。

### 3.2 对外头文件

对外头文件只允许包含其他模块使用的内容：

- 对外函数声明。
- 对外结构体和枚举。
- 对外必须了解的常量和宏。
- 跨模块共享的存储布局或报文布局。

以下内容不得放入对外头文件：

- 仅在模块内部使用的函数声明。
- 模块内部控制块和私有状态。
- 仅供单个 `.c` 文件使用的宏、枚举和结构体。
- 模块全局变量声明。
- 与对外接口无关的头文件。

### 3.3 头文件规则

- 每个对外头文件必须有唯一的包含保护符。
- 头文件必须自包含，单独包含时应能通过编译。
- 禁止头文件循环依赖。
- 只包含当前头文件实际需要的依赖。
- 使用其他模块接口时必须包含其对外头文件。
- 禁止在 `.c` 文件中使用 `extern` 绕过头文件声明。
- 禁止在头文件中实现普通函数。

```c
#ifndef APP_INC_ORDER_H
#define APP_INC_ORDER_H

#include <types.h>

/* 对外类型和接口。 */

#endif /* APP_INC_ORDER_H */
```

### 3.4 源文件组织

源文件按需要使用以下分段，空分段可以省略：

```c
/*-----------------------------------------------------------------------------
 Section: Includes
 -----------------------------------------------------------------------------*/

/*-----------------------------------------------------------------------------
 Section: Macro Definitions
 -----------------------------------------------------------------------------*/

/*-----------------------------------------------------------------------------
 Section: Type Definitions
 -----------------------------------------------------------------------------*/

/*-----------------------------------------------------------------------------
 Section: Private Variables
 -----------------------------------------------------------------------------*/

/*-----------------------------------------------------------------------------
 Section: Private Functions
 -----------------------------------------------------------------------------*/

/*-----------------------------------------------------------------------------
 Section: Public Functions
 -----------------------------------------------------------------------------*/
```

同一文件内的私有函数一般不需要在文件头集中声明。仅在函数调用顺序无法自然安排或
存在相互调用时增加必要的私有函数原型。

## 4. 排版

### 4.1 缩进和换行

- 禁止使用 TAB 字符。
- 每级缩进使用 4 个空格。
- 不得通过空格制造依赖编辑器宽度的复杂对齐。
- 相对独立的逻辑块之间应保留一个空行。
- 变量声明与后续执行语句之间应保留一个空行。
- 逻辑表达式需要换行时，`&&`或`||`应放在续行开头。

### 4.2 行宽

- 去除注释后的代码、声明、定义和宏应控制在 100 个字符以内；超过时按语义换行。
- 注释不纳入 100 个字符硬限制，但应保持便于阅读和评审。
- 静态配置表和协议规则表中的单行表项不受 100 个字符限制，但仍应保持清晰且便于阅读。
- URL、路径、日志字符串、协议字符串和无法合理拆分的宏允许超过 100 个字符。
- 例外代码行应控制在 120 个字符以内；确实无法合理拆分时允许超出并保持可读。
- 不得通过使用含义不清的缩写来满足行宽。

### 4.3 花括号

- `if`、`else`、`for`、`while` 和 `do` 的执行体必须使用花括号。
- 左右花括号分别独占一行。
- `case` 和 `default` 与 `switch` 内部代码保持同级风格。

```c
if (result == OK)
{
    session_start();
}
else
{
    session_stop();
}
```

### 4.4 空格

- 逗号后加一个空格。
- 双目运算符两侧各加一个空格。
- 单目运算符与操作数之间不加空格。
- `.`、`->` 前后不加空格。
- 控制关键字与左括号之间加一个空格。
- 函数名与左括号之间不加空格。
- 行尾不得包含空白字符。

```c
if ((connector > 0u) && (connector <= MAX_POINT_NUM))
{
    session->energy = current_energy + delta_energy;
}
```

## 5. 命名

### 5.1 通用规则

- 采用 Linux 风格：函数和变量使用小写 `snake_case`。
- 名称必须准确表达用途，禁止使用汉语拼音。
- 名称应简洁；作用域已经明确的语义不得在变量、枚举或结构体名称中重复堆叠。
- 除通用缩写外，不得随意缩写单词。
- 循环计数可以使用 `i`、`j`、`index` 等简短名称。
- 禁止局部变量与模块静态变量同名。

### 5.2 函数

- 函数名应以动作或动词短语为核心。
- 对外函数应带模块前缀，如 `order_init()`、`chan_send()`。
- 文件内部函数在不产生歧义时可以省略模块前缀。
- 获取、设置、创建和销毁接口应成对使用一致的词汇。

### 5.3 类型

- `typedef` 类型名以 `_t` 结尾。
- 枚举类型名以 `_e` 结尾。
- 结构体标签和枚举标签使用小写 `snake_case`。
- 枚举成员使用大写 `SNAKE_CASE`，并带模块前缀。
- 布尔变量和函数应表达状态或判断语义。

```c
typedef enum order_state_e
{
    ORDER_STATE_IDLE = 0,              /**< 当前没有活动订单。 */
    ORDER_STATE_CHARGING,              /**< 订单处于充电状态。 */
    ORDER_STATE_STOPPING               /**< 订单正在结束。 */
} order_state_e;
```

### 5.4 宏和常量

- 宏使用大写 `SNAKE_CASE`，并带模块前缀。
- 文件内部宏也应避免与其他模块重名。
- 数值应带符合类型的后缀，如 `10u`、`1000ul`。
- Dstor/TMN ID 在 `param_req_t` 初始化位置直接使用编号，不为单次使用的 ID
  额外定义宏。

## 6. 类型、变量与数据结构

### 6.1 变量

- 变量必须在首次使用前初始化。
- 在当前编译模式允许时，变量应声明在最小作用域并靠近首次使用位置；受 C 语言模式限制时，在所属
  代码块开头声明并立即给出安全初值。
- 一个变量只能表达一种含义。
- 严禁读取未初始化变量。
- 应减少全局变量，文件内部状态必须使用 `static`。
- 模块状态不得通过全局变量向外暴露，应提供函数接口。
- 不变参数和只读指针应使用 `const`。

### 6.2 数据类型

- 对协议、存储、硬件寄存器和跨模块接口使用明确宽度的项目基础类型。
- 协议、存储、跨模块布局和可能溢出的计算不得依赖 `int`、`long` 的编译器宽度；仅限作用域内且
  取值范围明确的循环计数或库接口适配可以使用原生整数类型。
- 有符号数和无符号数混合运算前必须确认取值范围。
- 强制类型转换必须确认符号、宽度、对齐和截断风险。
- 字符 I/O 函数返回值需要与 `EOF` 比较时，使用 `int` 接收。

### 6.3 结构体和枚举

- 结构体应描述一个职责明确的对象，不得成为无关状态的集合。
- 相同生命周期、相同所有者的状态可以组成模块控制块统一初始化。
- 仅协议报文、持久化布局或硬件要求精确布局的结构体使用显式对齐；普通内存结构保持编译器自然对齐。
- 需要 1 字节对齐时，使用 `#pragma pack(push, 1)` 和 `#pragma pack(pop)` 成对控制，并说明布局依据。
- 协议和存储结构必须明确字节序、字段长度、对齐、单位和版本兼容要求。
- 枚举用于表达有限状态，不得用裸 `uint8` 代替有明确语义的枚举。
- 枚举写入协议或存储前必须确认编译器宽度，不得直接依赖未约定的枚举大小。

## 7. 函数与接口

### 7.1 职责和规模

- 一个函数只完成一件事情。
- 新增函数超过 50 行、控制块嵌套超过 4 层或参数超过 5 个时，应评估拆分、提前返回或上下文结构体；
  保持现状更清晰时可以不拆分，并在评审中说明原因。这些数值是复杂度提示，不是机械验收线。
- 复杂函数应按业务步骤拆分，不得仅为减少行数机械拆分。

### 7.2 参数

- 模块间接口必须检查指针、长度、范围和状态。
- 缓冲区指针必须同时传入容量。
- 输出参数必须在成功返回前完整赋值。
- 输入参数放在输出参数之前。
- 不修改的输入缓冲区使用 `const`。
- 同一模块的参数检查责任必须保持一致。

### 7.3 返回值

- 必须检查可能失败的函数返回值。
- 不得无理由丢弃错误码。
- 主动忽略返回值时使用 `(void)`，并确保失败不会影响正确性。
- 错误出口必须释放本函数已经取得所有权的资源。
- 接口注释必须明确资源和缓冲区所有权转移规则。

### 7.4 可见性

- 文件内部函数必须声明为 `static`。
- 文件内部变量必须声明为 `static`。
- 对外接口保持最小集合，不得为内部实现便利扩大公开 API。

## 8. 宏、常量与预处理

- 宏表达式和宏参数必须使用完整括号。
- 多语句宏必须使用 `do { ... } while (0)`。
- 宏参数不得在宏内部发生自增、自减等副作用。
- 优先使用函数或 `static inline` 函数代替函数式宏。
- 只读常量优先使用 `const`，编译期开关和数组长度可使用宏。
- 禁止在宏中使用难以察觉的 `return`、`goto`、`break` 或 `continue`。
- 禁止为只使用一次且语义已由类型或上下文明确的数值建立宏。
- 条件编译块超过数行时，`#endif` 后应注释对应条件。

## 9. 注释与文档

### 9.1 基本要求

- 注释使用中文，协议名称、标准术语和无法准确翻译的内容可以保留英文。
- 注释解释设计意图、约束、单位和原因，不复述代码表面行为。
- 注释必须随代码同步更新。
- 公共接口和需要生成文档的内容使用 Doxygen；函数内部普通注释可以使用 `/* ... */` 或 `//`，
  同一局部区域保持一致。
- 公共宏、配置宏、状态枚举和存在非显然约束的结构体成员必须有清晰注释。

### 9.2 文件注释

```c
/**
 ******************************************************************************
 * @file       order.c
 * @brief      订单模块对外接口实现。
 * @details    接收启动和停止命令，维护订单任务及业务状态。
 * @copyright  Copyright(C), 2021-2031, JoysonQuin, Ltd.
 ******************************************************************************
 */
```

### 9.3 函数注释

新增或修改的公共函数必须使用完整 Doxygen 函数头。文件内部函数在职责、参数、返回值、所有权或
副作用不能从名称和代码直接看清时，也必须使用完整函数头；简单私有辅助函数不要求为满足格式而
添加重复代码语义的注释。函数头紧邻函数声明或定义，按以下顺序填写：

1. `@brief`：用动宾短语说明函数职责，不复述函数名。
2. `@param[in]`、`@param[out]` 或 `@param[in,out]`：按形参顺序逐项说明含义；无形参时省略。
3. `@retval`：每种返回值单独占一行并说明含义；无返回值时写 `@retval None`。
4. `@details`：仅在需要说明执行时机、边界、所有权或副作用时填写。

需要完整函数头时统一使用下列边框和排版，不得混用 `/** 简述。 */`、普通块注释或 `//`：

```c
/**
 ******************************************************************************
 * @brief      提交订单启动命令。
 * @param[in]  command:启动命令，函数在返回前完成内容复制。
 * @retval     OK:命令已接收。
 * @retval     ERR:参数非法或任务不可用。
 *
 * @details    本函数不接管command缓冲区所有权。
 ******************************************************************************
 */
```

### 9.4 数据结构注释

- 公共结构体和具有复杂生命周期的内部结构体应说明对象用途和生命周期。
- 成员存在单位、范围、无效值或所有权约束时必须说明；语义已经由名称和类型完整表达时不重复注释。
- 协议结构体注释应包含帧类型码。
- 公共枚举及状态机枚举的每个成员都必须有注释；局部、语义显然的内部枚举可以按组说明。
- 其他模块会使用的存储结构必须详细说明版本和兼容要求。

## 10. 安全编码

### 10.1 内存边界

- 禁止数组、指针和缓冲区越界。
- 字符串缓冲区必须为结尾 `'\0'` 预留空间。
- 二进制数据长度不得使用 `strlen()` 计算。
- 调用 `memcpy()`、`memset()` 前必须确认地址和长度有效。
- 禁止使用 `gets()`；处理外部输入或长度不确定的数据时禁止使用无长度限制的 `sprintf()`、
  `strcpy()` 和 `strcat()`，必须改用可验证容量的实现。
- 使用安全函数时仍必须检查返回值和截断结果。
- 释放动态资源后应将对应指针置为 `NULL`。

### 10.2 整数运算

- 除法前必须检查除数。
- 移位位数必须小于操作数宽度。
- 计算长度、时间和金额时必须评估上溢和下溢。
- 大类型转换为小类型前必须检查范围。
- 时间差和 Tick 超时判断应考虑计数回绕。

### 10.3 控制流程

- `switch` 必须包含 `default` 分支。
- 完整的 `if ... else if` 状态分类应以 `else` 结束。
- 不得混淆赋值、比较、逻辑和位运算符。
- 避免使用 `goto`；仅允许用于集中释放多项资源等能明显提高清晰度的场景。

## 11. RTOS、并发与资源

- 可被多个任务调用的函数必须具备可重入性，或明确使用互斥保护。
- 中断、回调和通道接收路径禁止无限阻塞。
- 消息队列投递应明确阻塞策略、超时策略和失败处理。
- 不得在持锁状态下执行可能长期阻塞的网络、存储或日志操作。
- 任务循环必须主动让出 CPU，或阻塞等待事件、队列、信号量。
- 任务栈大小必须根据局部变量、调用深度和库函数栈消耗评估。
- 申请队列、信号量、定时器、文件、Socket 和内存后必须检查结果。
- 每个资源必须有唯一且明确的释放位置。
- 消息、`appbuf_t` 和 `pbuf_t` 的所有权必须在接口注释中说明。
- 驱动、中断和硬实时回调路径禁止动态申请内存；通道收包和高频周期路径确需使用动态内存时，
  必须复用现有内存机制并证明时延、失败处理和回收路径可控。
- 大缓冲区不得未经评估直接放入任务栈或动态堆；应根据容量、生命周期、并发访问和 RAM 预算选择
  静态区、固定池、模块工作区或现有分配器。
- 新增或扩大任务栈必须评估局部变量、调用深度和库函数栈消耗。

## 12. 日志、错误与诊断

- 使用模块对应的 `trace` 类型输出日志。
- 必须复用项目已有日志机制和错误码，不得自行建立平行体系。
- 日志应包含定位问题所需的状态、协议、功能码、通道和错误码。
- 禁止在高频路径持续打印大块数据。
- 密钥、证书、密码和完整鉴权信息不得写入日志。
- 源码、示例和文档不得记录真实密钥、密码或私有证书；确需默认凭据时必须通过项目批准的配置或
  安全注入机制管理，并在文档中使用占位符。
- 错误日志应说明失败动作和原始错误码，不得只打印“失败”。
- 队列满、内存申请失败、发送失败和报文丢弃必须可诊断；低频路径可以记录限频日志，高频或影响
  在线运行的路径应提供独立统计，避免持续刷屏。
- 日志字符串原则上保持完整，避免仅为满足行宽而破坏检索。

## 13. 效率与资源占用

- 优先优化算法、数据布局和重复缓存，不做未经测量的微优化。
- 不得在多个模块重复缓存可从唯一数据源读取的状态。
- 大型证书、JSON 缓冲区和协议工作区应评估放置位置和生命周期。
- 只读表和只读适配器对象使用 `const`，放入只读存储区。
- 高频申请的小对象应评估使用固定池；驱动和中断路径避免动态内存。
- 循环中的不变量应移到循环外计算。
- 数据结构调整应同时评估 RAM、Flash、存储布局和升级兼容性。

## 14. 第三方代码与历史代码

- 第三方源码原则上不做无业务必要的格式化。
- 第三方代码必须通过独立目录和适配接口隔离。
- 修改历史代码时，只整理本次涉及的范围，不进行无关的大规模格式化。
- 修改文件时必须保留原有文件编码和换行格式，不得因局部修改转换整个文件。
- 新增代码不得继续复制已经确认不符合规范的历史写法。
- 规范迁移应分模块逐步进行，并与功能修改分开审查。
